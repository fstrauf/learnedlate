# Where to Start With AI (Without Buying a Platform First)

**Where to start with AI** is a sequence, not a shopping list: pick one owned workflow, run a thin readiness check, pilot it for 30 days with human review, and only then decide whether to buy a tool, assemble a stack, or bring in help. If you cannot name the process, the weekly volume, and the person who still owns it on day 31, you are not starting—you are collecting licences.

This page is for mid-market and founder-led teams (including ANZ operators) who already believe AI matters and are stuck on the first move. It is not a catalogue of tools, and it is not a 90-day transformation programme.

## The starting mistake most teams make

The search query sounds like a technology question. It is an operating question.

Teams that stall usually do one of these first:

| First move | Why it feels smart | What actually happens |
|------------|--------------------|------------------------|
| Buy ChatGPT / Copilot seats | “Everyone should try it” | Usage spikes, then dies; no process changes |
| Launch an all-staff chatbot | Visible, demo-friendly | No owner, no baseline, no write-back to systems |
| Run a six-month strategy offsite | Looks thorough | No shipped slice; the next budget cycle starts empty |
| Compare five vendors | Feels like due diligence | Decision theatre; still no before/after number |

A useful start is boring: **one workflow**, **one metric**, **one owner**.

If you already have a shortlist of candidate processes, jump to the [first AI use case scorecard](/blog/first-ai-use-case). If you do not even know whether data, skills, or governance would block a thin slice, run a light [AI readiness assessment](/blog/ai-readiness-assessment) in parallel—do not use readiness as a reason to never ship.

## A 30-day sequence you can actually run

### Days 1–5: Name the workflow, not the model

Write this on one page:

1. **Process** — e.g. inbound email that becomes a job, a ticket, or a CRM note  
2. **Volume** — how many similar items per week  
3. **Pain** — hours, delay, or error cost if it stays manual  
4. **Owner** — a named role, not “the AI committee”  
5. **Error cost** — what happens if the model is wrong, and can a human catch it?

If any of those five is blank, stop. You do not have a starting point yet.

**Worked example (service business, ~40 inbound emails/week):** quotes and change requests land in a shared inbox. Two coordinators spend ~6 hours/week copying fields into a job system and chasing missing details. Errors are recoverable (a human can fix a wrong suburb or date). Owner: operations lead. That is a start. “We should use AI for customer experience” is not.

### Days 6–10: Thin readiness, not a consulting theatre

Score only what would block *this* workflow:

| Check | Pass looks like | Fail looks like |
|-------|-----------------|-----------------|
| Data access | You can export 20–50 real examples this week | Everything lives in one person’s head or a locked mailbox |
| Permission | Legal/ops will allow a human-reviewed pilot | Customer data cannot leave the current system at all |
| Integration | You can paste, CSV, or hit one API | The system of record has no export and no write-back path |
| Review | Someone will check outputs daily for 30 days | “We’ll let the model run unsupervised” |

Three fails → pick a smaller workflow. One fail → fix that constraint before you buy anything.

A full six-dimension readiness pass is still useful later (strategy, data, infrastructure, talent, culture, governance). It is not the first week’s job unless you have *no* candidate process.

### Days 11–25: One thin slice with a human in the loop

The pilot is not “roll out AI.” It is:

- Baseline the current metric (hours, cycle time, error rate) for two weeks of history if you have it, or one honest week if you do not  
- Run the model on the same inputs the team already handles  
- Human reviews every output  
- Write the result back the same way you do today (even if that is still copy-paste)  
- Log misses: wrong field, hallucinated fact, skipped exception  

This is the same shape as a first [AI workflow automation](/blog/ai-workflow-automation) pilot. You are testing whether the *process* can absorb a model, not whether a vendor’s demo looks clever.

**Do not** train a custom model. **Do not** rebuild the inbox. Buy or assemble is almost always enough for a first slice—see the [AI build vs buy](/blog/ai-build-vs-buy) scorecard if someone is already arguing for a platform.

### Days 26–30: Keep, kill, or scale

Force a written decision:

| Decision | When it is honest |
|----------|-------------------|
| **Keep** | Metric moved, owner still wants it, errors are reviewable |
| **Kill** | No metric movement, or the team stopped reviewing |
| **Scale** | Keep *and* you can name the next adjacent workflow |

If the answer is keep/scale and the team cannot run it alone, that is when an [AI implementation partner](/blog/ai-implementation-partner) is a product decision—not a substitute for the first 30 days.

## What “start” looks like for three common teams

**Founder-led, <30 people.** Start in the founder’s own bottleneck (quoting, inbox triage, weekly reporting). Do not start with a public chatbot. A short [how to use AI for small business](/blog/how-to-use-ai-for-small-business) playbook is fine *after* the workflow is named.

**Mid-market ops-heavy.** Start where two systems already hand off badly (email → job system, CRM → finance, support → engineering). Volume is your friend; uniqueness is not required.

**Regulated or high-stakes decisions.** Start on an *internal* draft/extract/classify task with mandatory review. Do not start on unsupervised customer-facing decisions. Write the review rule on the same one-pager as the workflow—do not wait for a perfect policy to name the process.

## A 30-minute starter workshop (use it this week)

Put the owner and two people who do the work in a room:

1. List the five most annoying weekly processes (10 min)  
2. Score each 1–5 on volume, pain, data access, error recoverability, owner (10 min)  
3. Pick the highest score that is *not* a 1 on error cost (5 min)  
4. Book the 30-day calendar and the daily review slot (5 min)

Walk out with a one-pager, not a vendor shortlist.

If the room cannot agree on a process, you have a strategy problem, not a model problem: which outcomes matter this quarter, and which processes are allowed to change. Use the [AI readiness assessment](/blog/ai-readiness-assessment) to force that conversation before you buy another tool.

## What to ignore until you have a number

- Model bake-offs (“Claude vs GPT vs Gemini”) before a workflow exists  
- Company-wide prompt training with no process change  
- “AI centre of excellence” staffing before one slice ships  
- Custom model training for a first use case  
- Replacing a working SaaS feature with a homegrown bot  

Those can be later chapters. They are not where to start with AI.

## FAQ

**Where should a business start with AI?**  
Start with one painful, repeated workflow that has an owner and a baseline metric. Do a light readiness check on data and risk, then run a 30-day pilot with human review—do not start by buying a platform or launching a company-wide chatbot.

**What is the first step of an AI project?**  
Name the process, the weekly volume, and who owns the outcome after week four. If you cannot name those three, you are shopping for tools, not starting an AI project.

**Should we do an AI readiness assessment before any pilot?**  
A lightweight readiness pass is enough when one workflow already has usable data and a willing owner. A full six-dimension assessment is worth it when you do not know which process to pick or when data, skills, or governance would block even a thin slice.

**What should we not do first with AI?**  
Do not start with a company-wide chatbot, a model bake-off, or five overlapping licences. Those burn budget and political capital before anyone has a before/after number.

**How long should the first AI experiment take?**  
Plan 30 days from baseline to a keep/kill/scale decision. If the first slice needs a data lake or a programme office, you picked the wrong starting point.
